# 数据库 V2 结构方案

**项目：**世界一流大学“语言+人工智能”复合型人才培养模式研究  
**阶段：**第二阶段——数据库结构设计  
**版本：**V2 提案，待确认后实施  
**编制日期：**2026年11月24日

## 一、设计目标与实施边界

本方案依据第一阶段对现有 9 张表、4 所示范高校及 56 份 Word、16 份 PDF 的实际检查结果制定，目标是在不推翻现有成果的前提下，支持后续高校持续增加、逐条来源追溯和网页多维展示。

1. **保持既定六维分析框架不变：**培养目标、课程体系、师资配置、实践环节、评价机制、科研平台与相关机构。科研项目、代表性成果、学生培养与发展属于培养成效扩展信息，不替换或改名六维框架。
2. **保留现有 9 张业务表及全部记录 ID。**通过新增字段、关联表和证据表升级，不直接删除旧数据，不在原数据库上边运行边改结构。
3. **区分正式学位项目与科研培养路径。**学位项目、专业方向、M1／M2 阶段、科研团队、博士后计划、夏令营等均以类型和层级表达，不强行归为本科、硕士或博士专业。
4. **保留原文和层级。**结构化字段之外保留原始文本、标题路径、表格坐标和解析批次；不能可靠归类的信息进入待核验清单。
5. **来源与附件可追溯。**区分原始汇编、官方网页、官方 PDF 和本地附件；一条业务记录可有多个来源，来源可定位到段落、表格行或 PDF 页码。
6. **不推断缺失信息。**未公开、不适用、未采集、待核验分别处理；不编造 URL、访问日期、教师、课程、项目或学生去向。
7. **本阶段只确定方案。**经确认后才建立备份、生成 V2 新库、迁移旧数据并逐校导入。

### 2.1 核心关联关系

- 一所高校可拥有多个培养项目、课程、教师、平台、科研项目、成果和学生发展记录。
- `programs.parent_program_id` 支持“学位项目→专业方向／学段”的自关联层级；`host_organization_id` 可指明科研团队或平台承载关系。
- `programs` 与 `courses` 通过 `program_course` 形成多对多关系；课程实体只建一次，不同项目可拥有不同模块、学期、学分和必修选修属性。
- `faculty` 与 `organizations` 通过 `faculty_organization` 形成多对多关系；同一教师可在多个平台任职，不重复建立教师实体。
- `research_projects`、`research_outputs` 分别通过对应关联表连接教师、平台和培养项目。
- `sources`、`attachments`、`raw_fragments` 通过 `source_links` 为任意业务记录提供证据；一条记录可保留“汇编出处＋官方核验＋PDF 页码”等多条证据。
- `review_issues` 可指向具体高校、业务记录、原文字段或原文片段，形成可关闭、可复查的待核验流程。

### 2.2 通用字段与值域规则

以下规则适用于各业务表，字段表中不重复解释：

- `raw_text TEXT`：该记录对应的原始文本，不做摘要替换；表格记录可同时保留单元格原文。
- `review_status TEXT`：`draft`（机器初稿）、`pending_review`（待核验）、`verified`（已核验）、`conflict`（来源冲突）。
- `created_at TEXT`、`updated_at TEXT`：ISO 8601 格式时间，仅表示数据库操作时间，不冒充资料访问日期。
- 原各表单一 `source_id` 迁移至 `source_links`；V2 不以该字段作为唯一追溯机制，旧应用兼容由迁移期视图承担。
- 空值不使用统一“未注明”掩盖原因。重要字段的缺失原因写入 `review_issues.field_name` 和 `issue_type`，区分为 `not_public`、`not_applicable`、`not_collected`、`pending_review`。
- 标签字段使用 `yes`、`no`、`unknown`，只有原文或明确官方资料支持时才标为 `yes`；不得因记录属于 AI 项目就自动把全部课程或教师标为 AI 强关联。
- ID 使用稳定 TEXT 主键；已有 `U001`、`P001` 等 ID 不变。所有数据库连接均启用 `PRAGMA foreign_keys=ON`。

## 三、原有 9 张表的保留与增强

**主键：**`university_id`。  
**主要约束：**中文名与英文名分别建立规范化索引；同一高校的中英文规范名称组合唯一；`official_website` 不根据校名猜测。

| 字段 | 类型 | 含义与约束 |
|---|---|---|
| `university_id` | TEXT | 主键，保留现有高校 ID |
| `university_name_cn` | TEXT | 规范中文校名，必填 |
| `university_name_en` | TEXT | 规范英文校名，按原文或官方资料填写 |
| `name_aliases` | TEXT | 原始资料中的别名，以分隔列表保存，如“巴黎萨克雷大学／巴黎-萨克雷大学” |
| `country` | TEXT | 国家或地区规范值，必填 |
| `region` | TEXT | 统一地理区域值，用于驾驶舱统计 |
| `university_type` | TEXT | 高校类型，仅在有资料依据时填写 |
| `ranking_info` | TEXT | 排名信息及年份原文；非本项目必填项 |
| `official_website` | TEXT | 高校官方主页，须来自资料或经官方核验 |
| `collection_year` | INTEGER | 原采集年份，保留旧数据语义 |
| `data_status` | TEXT | `not_started`、`extracted`、`partial`、`reviewed` |
| `completeness` | TEXT | 仅保留旧值备查；网页完整度改由质量视图计算 |
| `notes` | TEXT | 数据范围与特殊说明 |

另加通用字段 `review_status`、`created_at`、`updated_at`。

## 四、新增 12 张表

### 4.1 `program_course`：项目—课程多对多关系

**主键：**`program_course_id`。  
**外键：**`program_id→programs`；`course_id→courses`。  
**设计理由：**同一课程可服务多个项目或学段；课程本身只存一次，项目内的模块、学期和学分可不同。

| 字段 | 类型 | 含义与约束 |
|---|---|---|
| `program_course_id` | TEXT | 主键，使关系本身也可关联来源和待核验事项 |
| `program_id` | TEXT | 培养项目外键，必填 |
| `course_id` | TEXT | 课程实体外键，必填 |
| `module` | TEXT | 核心、方向、开放选修、软技能等原文模块 |

## 五、约束、索引与统计视图

### 5.1 必须实施的数据库约束

1. 所有主键非空且唯一；业务外键启用 `ON UPDATE CASCADE`，删除默认采用 `RESTRICT`，避免误删高校时连带清除证据。
2. 高校名称、项目、课程代码、教师主页、DOI、附件哈希等建立适当的普通或唯一索引；允许为空的字段不被错误强制唯一。
3. `program_course`、`faculty_organization` 建立关系去重索引；对可空字段使用规范化表达式索引，避免 SQLite 的 NULL 语义造成重复。
4. 科研关联表使用 CHECK 保证每行至多有一个目标外键；三类外键均为空时，`linked_name_raw` 必填并须有对应待匹配事项。`source_links` 使用 CHECK 保证至少有一种证据载体。
5. 通用 `entity_type＋entity_id` 由触发器在证据／问题记录新增、更新及目标业务记录删除、主键变更时验证，禁止不存在的表名、孤记录和非法维度值；`review_issues` 中两字段必须同时为空或同时非空。
6. 原始附件和原文片段只允许新增或标记失效，不因业务实体去重而物理删除。
7. `raw_fragments.disposition` 与其证据关系、核验事项联动检查，确保 `mapped`、`raw_only`、`issue_created` 的含义可核验，而不是仅填写状态文字。
8. `objectives`、`practice`、`evaluation`、`student_development` 的 `scope_type=program` 时 `program_id` 必填；为 `university`、`cross_program` 或 `pending_review` 时不得伪造项目外键，后两者按规则保留说明或待核验事项。

### 5.2 建议视图

| 视图 | 用途 |
|---|---|
| `v_university_dimension_counts` | 每校六维及科研、成果、学生发展记录数，与网页指标共用同一口径 |
| `v_university_quality` | 按资料覆盖、已核验记录、来源追溯和待核验事项计算完整度，替代主观“高／中” |
| `v_source_traceability` | 每校及全库官方来源覆盖率、仅汇编出处记录数、无来源记录数 |
| `v_pending_review` | 按高校、严重程度和问题类型汇总待核验清单 |
| `v_duplicate_candidates` | 课程、教师、平台及附件的重复候选，不自动合并 |
| `v_export_counts` | SQLite 与 Excel 导出前后记录数核对 |
| `v_legacy_*`（9 个） | 按旧 9 表字段顺序提供迁移期只读兼容视图；现有网页仅切换读取映射，不重写详情交互 |

### 5.3 主要查询索引

- `programs(university_id, parent_program_id, program_kind, level)`。
- `program_course(program_id)`、`program_course(course_id)`。
- `faculty_organization(faculty_id)`、`faculty_organization(organization_id)`。
- 各业务表的 `university_id`、`review_status`。
- `source_links(entity_type, entity_id)`、`source_links(source_id)`、`source_links(attachment_id)`。
- `raw_fragments(attachment_id, sequence_no)`、`raw_fragments(parent_fragment_id)`。
- `review_issues(university_id, status, severity)`。

## 六、原始 Word／PDF 到 V2 的映射规则

### 6.1 解析顺序

1. **文件登记：**每校每批先建立 `import_batches`，将一校多文件的路径、哈希写入批次清单，再逐文件登记 `attachments.batch_id`；原始文件只读，`.DS_Store` 不入库。
2. **高校识别：**通过规范校名与别名表匹配 `universities`。例如“巴黎萨克雷大学”和“巴黎-萨克雷大学”映射到同一 `university_id`，同时保留两种写法。
3. **兼容性读取：**常规 DOCX 解析失败时检查包结构。南京大学、南洋理工大学、昆士兰大学、巴黎萨克雷大学采用只读 XML 兼容解析，并在附件中记录 `extraction_status`；不得把它们记为空文件。
4. **过滤目录：**根据 `toc` 样式、标题重复位置和正文顺序识别目录条目。不得简单删除所有以数字结尾的标题，避免误伤课程代码和真实年份。
5. **恢复标题层级：**综合 Word Heading、定制样式、outline level、Normal 中的 Markdown 标记和“一、／（一）／1.”编号，生成 `heading_path` 与 `parent_fragment_id`。
6. **保存原文片段：**标题、段落、表格行和 PDF 页文本先进入 `raw_fragments`，再生成业务实体；业务字段摘要不得覆盖原文。
7. **上下文映射：**从标题路径继承培养层次和项目提示，自动形成候选关联；`level_hint`、`program_hint` 只有经规则或人工核验后才写入正式外键。
8. **生成待核验：**无法识别学校、项目、来源或实体关系的片段保留在原文层，同时生成 `review_issues`，不强行挂到最相近专业。

### 6.2 章节与业务表映射

| 原文内容或标题 | 目标表 | 映射规则 |
|---|---|---|
| 学校名称、学校概况 | `universities` | 规范校名与别名同时保留；官方主页不得猜测 |
| 本科、硕士、博士、博士后 | `programs` | 形成培养层次节点；具体专业或方向继承该上下文 |
| 专业、方向、项目 | `programs` | 根据标题及正文区分学位项目、方向、科研路径和短期项目 |
| M1、M2 等学段 | `programs`＋`program_course` | 作为父项目下的 `stage` 或学段节点，课程通过关系表关联 |
| Miyao Group 等科研团队 | `programs`＋`organizations` | 可分别建立研究培养路径和科研平台，`is_formal_degree=0`，不伪造学位 |
| 培养目标、毕业要求、能力要求 | `objectives` | 优先关联当前项目；学校层面内容使用 `scope_type=university` |
| 课程设置、课程列表、课程表 | `courses`＋`program_course` | 课程实体与项目内属性分离；保留课程代码、名称、学分、模块和学时 |
| 实习、科研训练、项目训练、产学合作 | `practice` | 保留周期、学分、内容和考核；不能判断项目时允许为空并标记范围 |
| 评价方式、考核标准、论文要求 | `evaluation` | 保留评价方法、标准、权重和成果要求 |
| 实验室、研究中心、研究组、联盟 | `organizations` | 保留类型、上级机构、研究方向和合作信息 |
| 教师及团队成员 | `faculty`＋`faculty_organization` | 教师只建一次；不同团队的任职通过多对多关系表达 |
| 科研项目、资助项目、研究课题 | `research_projects`＋关联表 | 保留资助方、编号、起止时间、验收及负责人 |
| 论文、出版物、专利、软著、软件、模型、书籍、奖项 | `research_outputs`＋关联表 | 按类型分条保存，不压缩成教师或平台的一段笼统介绍 |
| 学生科研、在读成员、前成员、校友、升学就业 | `student_development` | 区分群体与个人，保留就读时段、成果和去向原文 |
| 官方网页 URL | `sources`＋`source_links` | 仅提取原文实际 URL；访问日期未知则为空 |
| 原始 Word、官方 PDF | `attachments`＋`source_links` | 保存文件指纹、路径、页数及与项目、维度、业务记录的关系 |
| 无法可靠判断归属的信息 | `raw_fragments`＋`review_issues` | 不新建虚假项目；保留学校层面、跨项目或待核验状态 |

### 6.3 标题变体与特殊案例

- “学科与专业设置”“学科和专业设置”作为同类章节候选；“学了与专业设置”等疑似错别字可以辅助定位，但必须保留原文并生成低严重度核验事项，不能静默改写。
- “学生发展”“学生培养”“人才培养”均映射到学生培养与发展候选章节；没有同名主章节时仍进行全文关键词检索，但不能仅凭一个“学生”词就批量建记录。
- “科研平台与关联机构”“科研平台与相关机构”统一映射至 `organizations`；网页显示使用“科研平台与相关机构”。
- 东京大学的 `Syntactic Parsing`、`Semantic Analysis` 等首先按研究项目／研究主题候选处理，不直接写入 `courses`；现有 8 条“课程／研究主题”在迁移时保留并标记类型复核。
- 巴黎萨克雷大学的中英对照课程表先按结构和来源配对，再生成共享课程候选；不能因两行名称翻译相同就自动合并，也不能把双语版本当成两倍课程量。
- 南京大学的科研项目表、论文、专利、软著、校友表分别映射到科研和学生表，不能只保留 NLP 方向的 17 条课程而丢弃培养成效信息。

### 6.4 无法判断归属时的处理

1. 能确定高校但不能确定项目：`university_id` 正常填写，`program_id=NULL`，按内容选择 `scope_type=university`、`cross_program` 或 `pending_review`。
2. 只能确定科研平台：保留平台关联，不反向猜测学位项目。
3. 教师或课程名称无法匹配实体：保留 `linked_name_raw` 和原文片段，生成重复或待匹配事项。
4. 同一来源出现冲突：两个版本均保留，业务记录标为 `conflict`，不得按较新文件时间自动覆盖事实。
5. 没有任何可靠归属：仅保存原文和待核验事项，不进入网页正式统计。

## 七、来源、访问日期与附件管理

### 7.1 证据链

每条重要记录尽量形成以下证据链：

**业务记录 → `source_links` → 官方 `sources` → 对应 `attachments`／`raw_fragments` → 页码、段落或表格行。**

同时保留两类不同作用的信息：

- `compiled_origin`：说明记录来自哪份原始汇编及其具体位置。
- `official_verification`：说明记录由哪个官方网页或 PDF 支持。

只有汇编出处而尚无官方来源的记录可以保留，但必须计入“仅汇编出处”数量，不能展示为“官方已核验”。

### 7.2 URL 与访问日期

- URL 同时从 Word 正文纯文本和外部超链接关系提取，清洗句号、括号等尾随标点，并保留原始写法。
- 不因高校名称推测官网，不把搜索引擎结果地址当作原始来源。
- 原资料有实际访问日期时沿用；本次真实重新访问时可记录新的核验日期；完全未知时为 NULL 并形成待核验事项。
- 数据库导入时间只写入 `created_at`，不得写入 `access_date`。
- 链接失效不立即删除来源，标记 `verification_status=unreachable` 并保留原文证据。

### 7.3 附件与本地文件

- 原始 56 份 Word 和 16 份 PDF 全部登记；后续新增官方 PDF 使用同一机制。
- 数据库存相对路径和 SHA-256，不把大型文件二进制写入 SQLite。
- `storage_status` 分开记录 `local_copy_present`、`official_link_only` 或 `unavailable`；`download_permission` 分开记录 `allowed`、`official_link_only` 或 `unknown`。许可不明时即使本地有文件，也不公开提供下载。
- 同一 PDF 可服务多个培养项目或维度，通过多条 `source_links` 关联，不复制附件。
- PDF 证据尽量记录页码；Word 证据记录标题路径、段落序号或表格行列。

## 八、旧数据无损迁移方案

### 8.1 迁移原则

采用“**备份原库→创建 V2 新库→迁移→双向核对→试运行→切换**”，不在唯一一份 `language_ai_cases.db` 上直接执行结构修改。

### 8.2 具体步骤

1. **备份与清单：**备份现有 SQLite、Excel、`app.py` 和配置文件，记录文件大小与 SHA-256；原始 Word／PDF 继续保持只读。
2. **创建 V2 新库：**按确认后的 SQL 建立 21 张表、约束、索引、触发器和视图，启用外键。
3. **迁移高校：**保留 `U001—U004` 及原字段；旧 `completeness` 仅作历史备查，重新计算质量视图。
4. **迁移项目：**保留所有 `program_id`；东京大学 Miyao Group 标记为科研培养路径、非正式学位，原 `level` 和 `degree` 文本保留供复核。
5. **迁移培养目标：**通过原项目补齐 `university_id`；已有项目关联保持不变。
6. **迁移课程：**保留旧 `course_id`，将旧 `courses.program_id` 及模块、学期、ECTS、学时写入 `program_course`。6 组同名课程只生成重复候选，迁移阶段不自动合并。
7. **迁移教师和平台：**保留教师及平台 ID；旧 `faculty.organization` 写入 `primary_unit_text`。只有名称和原文关系明确时才生成 `faculty_organization`，其余进入待核验。
8. **迁移实践与评价：**保留原项目关联及全部字段，补充高校和范围类型。
9. **迁移来源：**旧各表 `source_id` 转为 `source_links`。现有 4 条“案例资料汇编”标为 `compilation`、`is_official=0`，空 URL 保持不变；LISN 来源保留为官方来源。
10. **登记原始资料：**将 56 份 Word 和 16 份 PDF 加入附件表，记录哈希和解析状态；此步骤只登记，不代表其内容已全部结构化。
11. **双向核对：**核对旧库到新库的逐表记录数、ID 集合、字段非空值和抽样原文；任何旧记录未映射都必须进入迁移差异清单。
12. **兼容试运行：**通过迁移期兼容视图运行现有网页，确认首页 4／10／77／31／14 等指标不因结构升级而变化，再进入新功能开发。
13. **切换与回滚：**验证通过后生成一致的新 Excel，网页再切换至 V2；旧库和旧 Excel 永久保留为备份，出现阻断问题可回滚。

### 8.3 迁移不得执行的操作

- 不自动删除同名课程、教师或平台。
- 不把空字符串统一改成看似完整的占位描述。
- 不把 2026-09-15 直接认定为所有官方资料的实际访问日期。
- 不把汇编文档的整理时间当成官方发布日期。
- 不为了降低待核验数量而强行关联项目、教师或平台。
- 不在迁移阶段修改原始 Word、PDF 或覆盖上传文件。

## 九、逐校数据质量检查与验收标准

### 9.1 每校导入后的质量报告

每所高校生成独立质量报告，至少包含：

1. 输入文件清单、哈希、解析方式、解析器版本和导入批次。
2. 各业务表新增、更新、未变化记录数，以及与上一版的 ID 差异。
3. 原文片段总数、已映射数、仅保留原文数、待核验数；**未解释丢弃数必须为 0**。
4. 六维及科研、成果、学生发展覆盖情况；无公开信息的维度单独说明，不强行补齐。
5. 主外键、唯一约束、孤记录、重复 ID、非法枚举和空关键字段检查结果。
6. 教师、课程、平台和附件的重复候选及处理结论。
7. 官方来源覆盖率、仅汇编出处记录数、无来源记录数、失效链接数。
8. 至少按项目、课程、教师、平台、科研和学生发展分别抽样回查原文，记录抽样数量和一致率。
9. SQLite、Excel、网页三方记录数和关键统计一致性。
10. 待核验清单及高优先级问题；报告未关闭的问题不得隐藏。

### 9.2 全库验收底线

| 检查项 | 通过标准 |
|---|---|
| 原始文件登记 | 56 份 Word、16 份 PDF 均有附件记录和正确哈希；后续新增文件同样登记 |
| 旧数据保留 | 旧 9 表全部 ID 均可追溯，迁移差异均有解释，无静默删除 |
| 数据库完整性 | `integrity_check=ok`，`foreign_key_check` 无结果，关键字段非空 |
| 原文保留 | 所有解析片段均有去向，未解释丢弃数为 0 |
| 项目类型 | 科研团队、学位项目、方向、学段和短期项目可明确区分 |
| 多对多关系 | 共享课程不重复建实体；教师跨平台不重复建教师 |
| 来源追溯 | 每条正式展示记录有来源，或明确标为待核验；官方核验状态不混淆 |
| 附件关联 | 附件可定位高校，并能按需要关联项目、维度、来源和页码 |
| 数据一致性 | SQLite、Excel、网页总数及每校分项数量一致 |
| 术语与框架 | 六维框架不变，网页统一使用“科研平台与相关机构” |

## 十、第一阶段问题与 V2 对策对照

| 第一阶段发现 | V2 对策 |
|---|---|
| 52 所未入库、4 所部分入库 | 批次化原文解析、逐校质量报告，不把附件数量当作入库数量 |
| 无主键、外键和必填约束 | 完整 PK／FK／CHECK／UNIQUE、触发器和外键启用 |
| 课程只能属于一个项目 | `program_course` 多对多，项目内属性独立 |
| 教师无法规范属于多个平台 | `faculty_organization` 多对多 |
| 科研项目与成果无处保存 | 科研内容表及教师、平台、项目关联表 |
| 学生培养、就业和校友去向缺失 | `student_development` 同时支持群体和个人记录 |
| 来源只有单一 `source_id`，汇编与官方来源混杂 | `sources` 分类＋`source_links` 多证据链＋官方核验状态 |
| PDF 无法关联项目、维度和来源 | `attachments`＋`source_links`，支持多项目、多维度及页码定位 |
| 原文被压缩、无法回查 | `raw_fragments` 保存全文、标题路径和表格坐标 |
| 无法归类的信息可能被强行分配 | 可空项目外键、范围类型及 `review_issues` |
| 完整度“高／中”缺乏口径 | `v_university_quality` 按覆盖、来源和待核验情况计算 |
| 特殊 DOCX 读取失败 | 附件解析状态与 XML 兼容流程，不覆盖原文件 |

## 十一、确认后的实施顺序

1. 按本方案生成可执行 SQL、完整数据字典和迁移脚本，先备份并建立 V2 新库。
2. 迁移现有 4 所示范高校，运行旧网页兼容测试和迁移差异检查。
3. 以这 4 所为原文回查试点，补齐科研、成果、学生发展和证据链，提交逐校质量报告。
4. 规则稳定后分批处理其余 52 所；每批均可回滚，不影响已验收高校。
5. 数据核验完成后升级网页检索、比较、驾驶舱、详情、来源和附件功能。
6. 最终交付完整程序、SQLite、同步 Excel、原始资料目录、数据字典、质量报告、部署说明和可运行 ZIP。

**本方案确认前，不执行批量入库，也不删除或合并任何现有记录。**
